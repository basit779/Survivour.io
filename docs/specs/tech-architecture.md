# Technical Architecture & Project Setup Specification

> Subsystem owner doc for **"Wasteland Survivor"** (working title) — a Survivor.io-style bullet-heaven survival roguelite.
> Stack: **Vite + TypeScript → Canvas2D → Capacitor (iOS/Android)**. All art is programmatic. Target: **60 fps on a 2019-era mid-range phone (Snapdragon 660 / A11)** with **800–1500 active entities**.
>
> This document is the contract every other engineer builds against: folder tree, data-structure shapes, the loop, pooling, render pipeline, input, audio, and ship steps. Names are deliberately *adapted* from Survivor.io to avoid trademark issues (e.g. Kunai → **Shuriken Storm**, Lightchaser → **Aether Edge**, Void Power → **Singularity**, Lucille → **Spiked Lucy**).

---

## 0. Guiding principles (the "why" behind every choice)

| Principle | Consequence in this architecture |
|---|---|
| **Allocation in the hot loop = GC stutter = dropped frames.** Mobile JS GC pauses (10–40 ms) are the #1 cause of jank in bullet-heaven games. | Zero per-frame allocation. Everything that spawns/dies (projectiles, enemies, particles, gems, damage numbers) lives in **pre-allocated pools backed by typed arrays / struct-of-arrays**. No `new` inside `update()` / `render()`. No closures created per entity per frame. No array `.filter`/`.map`/spread in hot paths. |
| **Canvas2D fill-rate is the bottleneck, not JS.** Overdraw (big glows, full-screen gradients) kills mobile GPUs. | Pre-render every visual to an **offscreen sprite cache** once, then `drawImage` (cheap blit). Cap total particle count. Glow is baked, not drawn live. |
| **Determinism for replay/debug/balance.** | **Fixed timestep** simulation (60 Hz logical), seeded PRNG, render interpolation. |
| **Data-driven content.** Designers tune `.ts` data tables, not code. | All weapons/enemies/waves/passives/characters/meta are plain data objects with typed schemas. Systems read tables; adding content = adding a row. |
| **Ship to two stores from one codebase.** | Capacitor wrapper, no native plugins required for v1 beyond Haptics + StatusBar + SplashScreen. |

## 2. Entity model — **Data-oriented Struct-of-Arrays (SoA) pools**, not a generic ECS

### 2.1 Decision & justification

Three candidates were evaluated for ~1500 concurrent entities at 60 Hz on mobile JS:

| Approach | Verdict |
|---|---|
| **Full generic ECS** (entity id → archetype tables, query system, sparse sets) | **Rejected for v1.** Over-engineered; query iteration & archetype moves add overhead and indirection. The entity *kinds* here are few and fixed (player, ~8 enemy archetypes, projectiles, particles, gems, numbers). Generality buys nothing and costs cache locality + dev time. |
| **OOP class instances pooled** (`Enemy[]`, each with methods) | **Rejected.** 1500 polymorphic objects → poor cache behavior, megamorphic call sites deopt in V8, hidden-class churn, GC pressure from any transient props. |
| **Struct-of-Arrays per kind, index-based pools** (chosen) | **Chosen.** Each property is a contiguous `Float32Array`/`Int32Array`/`Uint8Array`. Iteration is linear over packed memory → cache-friendly, monomorphic, JIT-loves-it, **zero GC** (arrays allocated once at boot). This is exactly how high-entity-count web games (and the engines behind Vampire Survivors clones) avoid GC spikes. |

We call it **"ECS-lite"**: components = parallel typed arrays; entity = an integer index into those arrays; systems = plain functions iterating `0..count`. There is **no Entity object**.

### 2.2 The pool primitive

Each kind owns a `Pool` that manages slot lifetime via a **swap-remove dense packing** strategy (preferred for projectiles/particles where order is irrelevant) or a **free-list** (for enemies where stable ids help collision/targeting). Both keep iteration over `[0, count)` with no holes for the hot kinds.

```ts
// engine/Pool.ts — dense swap-remove variant (used for projectiles, particles, gems, dmg numbers)
export class Pool {
  capacity: number;
  count = 0;                // active entries occupy indices [0, count)
  constructor(capacity: number) { this.capacity = capacity; }

  /** Returns the new slot index, or -1 if full. Caller fills component arrays at this index. */
  alloc(): number {
    if (this.count >= this.capacity) return -1; // full → drop spawn (budgeted, see §2.4)
    return this.count++;
  }

  /** O(1) remove: copy last active entry into the freed slot. Returns the index that MOVED
   *  (so the caller can copy ALL component arrays from `moved` → `i`), or -1 if none moved. */
  free(i: number): number {
    const last = --this.count;
    if (i !== last) { /* caller copies arrays[last] -> arrays[i] */ return last; }
    return -1;
  }
}
```

> **Iteration safety rule:** because `free()` swaps the last element into `i`, systems that may free during iteration **must iterate backwards** (`for (let i = count-1; i>=0; i--)`) OR not advance `i` when a swap happened. This is the single most important footgun; it is documented at the top of every system that frees.

For **enemies** we use a stable free-list pool (ids don't move) because the spatial hash and damage queue reference enemies across systems within a frame:

```ts
// Stable-id pool
export class FreeListPool {
  capacity: number;
  alive: Uint8Array;        // 1 = slot occupied
  freeStack: Int32Array;    // stack of free indices
  freeTop: number;
  count = 0;                // live count (for HUD)
  highWater = 0;            // max index ever used → iterate [0, highWater)
  alloc(): number;          // pop free index, set alive=1, bump highWater
  free(i: number): void;    // alive[i]=0, push to freeStack
}
```

### 2.4 Capacity budget (hard caps → graceful degradation)

| Pool | Capacity | Bytes (approx) | Overflow behavior |
|---|---|---|---|
| Enemies | 1200 | ~70 KB | SpawnDirector throttles: stops spawning while at cap; never errors. |
| Projectiles | 2000 | ~110 KB | `alloc()==-1` → skip emission this frame for that weapon. |
| Particles | 3000 | ~110 KB | Oldest-die: emitters request N but get min(N, free); cosmetic only. |
| Gems | 600 | ~25 KB | If full, merge nearby gems (increase value of an existing one) instead of spawning. |
| Damage numbers | 256 | ~9 KB | If full, overwrite oldest (visual only). |

Total entity memory ≈ **~0.4 MB**, allocated once. This is the entire point: after boot, the simulation does **no heap allocation**.

## 3. Render pipeline (Canvas2D)

### 3.1 Canvas layering

Two **stacked `<canvas>` elements**, not one, and not N. Rationale: the world repaints fully every frame (it's a horde — nearly everything moves, so dirty-rect tracking is pointless and costlier than a clear+redraw). But **menus/overlays repaint rarely**, so isolating them avoids redrawing static UI each frame.

```
#game-world   z:0  — full clear + redraw every frame (camera-transformed world + HUD)
#game-overlay z:1  — joystick, level-up cards, pause menu, modals; redrawn only on change (dirty flag)
```
DOM (`ui/dom/overlay.ts`) sits at z:2 for text-heavy screens (shop lists, settings) where native text rendering & scrolling beat canvas.

**Redraw strategy:** World layer = **full redraw** (`clearRect` whole canvas then paint). This is correct for bullet-heaven — measured overdraw, not clears, is the cost. Overlay layer = **dirty redraw** (only `render()` when `dirty===true`).

### 3.2 DPI / retina handling

```ts
// Renderer.resize()
const dpr = Math.min(window.devicePixelRatio || 1, 2);   // CAP at 2: 3x DPR phones gain no visible
                                                          // quality for this art style but 2.25x the fill cost.
canvas.width  = Math.round(cssWidth  * dpr);
canvas.height = Math.round(cssHeight * dpr);
canvas.style.width  = cssWidth  + 'px';
canvas.style.height = cssHeight + 'px';
ctx.setTransform(dpr, 0, 0, dpr, 0, 0);                   // draw in CSS px; backing store is sharp.
ctx.imageSmoothingEnabled = false;                        // crisp programmatic shapes; faster blits.
```
Capping DPR at 2 is a deliberate **perf-for-free** decision: a 1080×2400 phone reports `dpr≈3`; uncapped that's ~7.8M backing pixels vs ~3.4M at dpr 2 — a 2.3× fill-rate saving with no perceptible loss on glow/shape art. If a device drops below 55 fps for 2s, an **adaptive quality controller** further drops effective DPR to 1.5 then 1.25 (see §3.6).

### 3.3 Draw order (z-layers, painted back-to-front each frame in `RenderSystem`)

1. **Background** — tiled procedural grid/parallax, scrolled by camera (drawn as a repeating baked tile, 1 `drawImage` per visible cell, ~30 cells).
2. **Ground decals/shadows** — soft baked shadow ellipse under each enemy/player (one cached sprite, alpha 0.25).
3. **Gems** (so they appear under monsters).
4. **Enemies** — sorted? No. **Y-sorting 1200 entities every frame is too costly**; instead enemies draw in store order. For this top-down style depth-sorting is unnecessary; overlap reads fine. (Boss draws last among enemies via a one-pass "draw non-boss, then draw boss" split — O(n), no sort.)
5. **Player.**
6. **Projectiles / weapon areas.**
7. **Particles** (additive sparks/explosions on top).
8. **Damage numbers.**
9. **HUD** (drawn in screen space — `ctx.setTransform` reset to identity*dpr).

Camera transform is applied once per frame: `ctx.translate(-camX+halfW, -camY+halfH)` around the world layers, then reset for HUD.

### 3.4 Baked sprite cache — the cheap-glow trick (`SpriteCache.ts`)

Glow, gradients, and soft circles are **murder** if drawn with live `ctx.shadowBlur` or `createRadialGradient` per entity per frame. Instead, at **BootScene**, we render every visual ONCE to an offscreen atlas and thereafter only `drawImage` (a hardware blit):

- For each enemy type, weapon projectile, gem tier, particle kind: render a small canvas (e.g. 48×48) containing the **baked glow + body** using `radialGradient` + `shadowBlur` *once*, store as an `ImageBitmap` (via `createImageBitmap`) or offscreen canvas tile.
- Runtime cost per entity = 1 `drawImage(tile, x-r, y-r)` ± a tint pass. No gradients, no shadows in the loop.
- **Hit flash**: instead of recoloring, keep a second pre-baked **all-white silhouette** tile per type; blend it on top with alpha = `flashT`. Two blits, still cheap.
- **Rotation/scale**: only projectiles that spin pay `ctx.rotate` (cheap relative to gradients).

Atlas is built deterministically from `data/palette.ts` + `data/enemies.ts` so designers control all visuals via data.

```ts
// SpriteCache API
bake(): void;                        // called once in BootScene
get(spriteId: number): SpriteTile;   // {bitmap, w, h, ox, oy}  (ox/oy = anchor offset)
```

### 3.5 Canvas vs DOM UI split

- **On-canvas (HUD, joystick, level-up cards, pause):** in-loop, animated, must sync with game — drawn on overlay/world layers.
- **DOM (main menu, character select, shop, settings, game-over results):** static-ish, text/lists/scroll-heavy, benefit from native rendering, accessibility, and `safe-area-inset` CSS. Managed by `ui/dom/overlay.ts`, shown/hidden per scene.

### 3.6 Aspect ratios & safe areas

- Design reference resolution: **logical 1280 × 720 "design units"**, but the game is **fit-by-width with vertical bleed** (portrait-friendly). We compute a **camera viewport in world units** scaled so the *narrow* dimension always shows a fixed amount of world (`VIEW_MIN_WORLD = 360 world-units tall`), and the long dimension shows more world (no letterboxing, no stretching). This is the Survivor.io approach: you simply see *more world* on taller screens — fair and bezel-free.
- **Fill, not letterbox.** Letterbox bars look cheap on mobile. We never distort aspect; we reveal more/less world.
- **Safe areas:** read `env(safe-area-inset-*)` via CSS custom props mirrored to JS; HUD and joystick anchors inset by these so notches/home-indicators never cover controls. `viewport-fit=cover` in `index.html`.
- Handle `resize` + `orientationchange` (debounced 100 ms) → `Renderer.resize()` → recompute camera scale + safe insets. Lock to **portrait** in Capacitor config (the genre's standard) but the code supports both.

### 3.7 Adaptive quality controller (in `Engine`)

Rolling 1s avg frame time. Tiers, stepping down on sustained <55fps, up on sustained >58fps:

| Tier | DPR cap | Max particles | Glow blits | Background |
|---|---|---|---|---|
| High | 2.0 | 3000 | on | parallax |
| Med | 1.5 | 1500 | on | static grid |
| Low | 1.25 | 600 | shadows off | flat color |

## 4. Game state machine

Implemented as a **stack-based `SceneManager`** (so overlays like LevelUp pause but keep RunScene rendered beneath). Each `Scene` implements `enter/exit/update/fixedUpdate/render/onInput`. Transitions support a 200 ms cross-fade.

```
            ┌──────────┐
            │   Boot   │  bake sprites, init save, prime audio (deferred until first touch)
            └────┬─────┘
                 ▼
            ┌──────────┐   Play ┌───────────────┐  confirm  ┌──────────┐
            │ MainMenu │──────▶ │ CharacterSelect│─────────▶ │   Run    │
            └────┬─────┘        └───────────────┘           └────┬─────┘
        Shop │   │ Settings                                       │
             ▼   ▼                                                │ (overlays push/pop)
        ┌─────────┐                          level-up ┌───────────▼──────────┐
        │MetaShop │◀───────────────┐                  │  LevelUp (pause+over)│  pick → pop → resume Run
        └────┬────┘                │                  └──────────────────────┘
             │ back to Menu        │ to Shop                     │
             ▼                     │              player hp<=0   ▼
        (MainMenu)            ┌────┴─────┐  ◀───────────  ┌──────────┐
                              │ GameOver │                │ Run dies │
                              └────┬─────┘                └──────────┘
                          Retry │  │ Menu
                                ▼  ▼
                          (CharSelect / MainMenu)
```

**Stack semantics:**
- `Run` is a **base scene**. `LevelUp`, `Pause`, `Chest` are **pushed overlays**: they set `RunScene.paused=true` (its `fixedUpdate` early-returns) but `RunScene.render` still runs underneath (frozen world), so the dimmed battlefield shows behind the cards. Popping resumes.
- `GameOver` **replaces** Run (Run's `World` is disposed → pools reset, arrays kept for reuse).
- Audio mood is set per scene (`enter()` → `MusicGen.setMood(...)`).

**Pause sources:** OS `visibilitychange` (app backgrounded) auto-pushes a silent pause + suspends `AudioContext`; manual pause button pushes the pause modal.

## 5. The game loop — fixed timestep + interpolation

### 5.1 The loop (`Engine.ts`)

Survival roguelites need **deterministic, frame-rate-independent simulation** (collision tunneling and weapon timing must not vary with fps). We run a classic accumulator: simulation at fixed **60 Hz** (`FIXED_DT = 1/60 s`), render as fast as RAF allows with interpolation `alpha`.

```ts
const FIXED_DT = 1 / 60;          // logical step
const MAX_STEPS = 5;              // spiral-of-death guard: clamp catch-up

loop(now) {
  let frameTime = (now - last) / 1000;
  last = now;
  if (frameTime > 0.25) frameTime = 0.25;        // tab-stall clamp
  accumulator += frameTime * timeScale;          // timeScale: 0 when paused, <1 slow-mo on level-up sweep

  let steps = 0;
  while (accumulator >= FIXED_DT && steps < MAX_STEPS) {
    scene.fixedUpdate(FIXED_DT);                  // ALL gameplay sim happens here
    accumulator -= FIXED_DT;
    steps++;
  }
  if (steps === MAX_STEPS) accumulator = 0;       // drop backlog rather than spiral

  const alpha = accumulator / FIXED_DT;           // 0..1 interpolation factor
  scene.update(frameTime);                        // non-sim: input sampling, UI anim, camera follow
  scene.render(alpha);                            // interpolate render positions between prev/curr
  requestAnimationFrame(loop);
}
```

> **Interpolation detail:** for the player + camera (where smoothness matters most) we keep `prevX/prevY` and render at `lerp(prev, curr, alpha)`. For 1200 enemies we **skip interpolation** (render at current pos) — at 60 Hz sim the visual diff is imperceptible and storing prev arrays for all enemies isn't worth the memory bandwidth. This is a measured trade-off, documented.

### 5.2 Integration with core-mechanics

`fixedUpdate(FIXED_DT)` is where the core-mechanics team's formulas live. `RunScene.fixedUpdate` calls systems in the order below; each system is `system(world, fdt)`. The **shared contract** is: core-mechanics provides the data tables (`data/`) + the per-system tuning; this architecture provides the stores, pools, loop, and call order. `FIXED_DT` is the canonical dt all damage/cooldown/speed numbers are expressed against (e.g. "speed 110" = 110 world-units/sec; integrated as `x += vx * fdt`).

### 5.3 System execution order (`RunScene.fixedUpdate`)

```
1.  PlayerControlSystem   (InputState → player vel; dash)
2.  WeaponSystem          (tick cooldowns; emit projectiles/areas)
3.  EnemyAISystem         (steer toward player; separation; ranged shoot)
4.  MovementSystem        (integrate pos from vel: player, enemies, projectiles, gems)
5.  StatusEffectSystem    (burn/slow/poison ticks; apply slowMul)
6.  ProjectileSystem      (lifetime, homing retarget, off-screen cull)
7.  SpatialHash.rebuild   (clear + insert all enemies for this step)
8.  CollisionSystem       (proj↔enemy, enemy↔player, gem↔player via hash queries)
9.  DamageSystem          (resolve hit queue: damage, crit, knockback, status, dmg numbers)
10. DeathSystem           (resolve death queue: drops, FX, free slots, kill count)
11. PickupSystem          (gem magnet, xp/gold accrual)
12. ProgressionSystem     (xp→level; on level-up push LevelUpScene, set timeScale ramp)
13. EvolutionSystem       (check evolve conditions)
14. SpawnDirector         (wave schedule → spawn enemies/elites/boss)
15. ParticleSystem        (integrate + fade)            // could move to update() since cosmetic
16. DamageNumberSystem    (float + fade)
17. CameraSystem.followFixed (record target for interpolation)
```
`update(dt)` (per-render-frame, not fixed): sample input, camera lerp+shake, HUD value tweens, adaptive-quality check.

## 6. Input abstraction

One funnel: each source writes into a shared, flat `InputState`; `InputManager.sample()` runs once per `update()` and merges sources by priority (last-active wins for movement; any-source for actions). Systems read **only** `InputState` — they never touch DOM events.

```ts
interface InputState {
  moveX: number;          // -1..1   (already dead-zoned & normalized)
  moveY: number;          // -1..1
  moveMagnitude: number;  // 0..1    (analog speed for joystick/gamepad; 1 for keyboard)
  dashPressed: boolean;   // edge (consumed)
  pausePressed: boolean;  // edge
  confirmPressed: boolean;// menus
  pointerX: number;       // screen px (for menu taps / card selection)
  pointerY: number;
  pointerDown: boolean;
}
```

- **VirtualJoystick** (primary, mobile): **floating** mode — first touch anywhere on the left 60% of the screen anchors the stick; drag vector / `maxRadius(=80px)` → `moveX/moveY`, with `deadZone(=8px)`. Right-screen taps reserved for future active items / menu. Multi-touch tracked by `pointerId`. Renders on the overlay layer.
- **Keyboard** (dev/desktop): WASD/Arrows → unit move vector (magnitude 1); `Space`=dash, `Esc`=pause, `Enter`=confirm. Debug: `~` toggles overlay (fps, entity counts, hitboxes), `1-9` force-spawn.
- **Gamepad**: poll `navigator.getGamepads()` each frame; left stick → move (apply 0.15 radial dead zone), `A`=confirm, `B`=dash, `Start`=pause.
- **Priority/merge:** if joystick active → it owns movement; else gamepad; else keyboard. Action edges OR-combined across all. This lets a tester use keyboard in the browser and the same build feel native on phone with zero code branches in systems.
- Touch listeners are `{passive:false}` on the canvas with `touch-action:none` CSS + `preventDefault` to kill scroll/zoom/pull-to-refresh.

## 8. Audio — 100% WebAudio synthesis (no files)

`AudioEngine` builds the graph: `ctx → masterGain → {musicBus, sfxBus} → destination`. **Unlock on first user gesture** (mandatory on mobile): the first canvas `touchstart`/`click` calls `ctx.resume()`. Suspend on `visibilitychange` hidden.

**SFX (`Sfx.ts`)** — each is a tiny synth recipe (oscillator/noise + ADSR gain envelope + optional filter sweep), one-shot, with a **voice cap (max ~16 concurrent)** and per-sound cooldown to avoid machine-gun clipping when 200 enemies die at once (e.g. `hit` debounced to ~1 trigger / 40 ms, layered with slight pitch randomization for variety).

| SFX | Recipe sketch |
|---|---|
| `hit` | short square blip 600→200 Hz, 40 ms decay, ±8% pitch jitter |
| `crit` | hit + bright triangle layer + tiny noise burst |
| `enemyDie` | noise burst through lowpass 2k→200 Hz, 90 ms |
| `explode` | white noise + sine 120→40 Hz body, 250 ms, lowpass sweep |
| `pickupGem` | sine 880→1320 Hz pluck, 60 ms (pitch rises with combo) |
| `levelUp` | 3-note ascending arp (C-E-G) triangle |
| `evolve` | rising saw sweep + shimmer (detuned sines), 700 ms |
| `playerHurt` | noise + sine 200 Hz, lowpass, 150 ms; + Haptics impact |
| `uiTap` | tiny sine click 8 ms |

**Music (`MusicGen.ts`)** — a step sequencer running off `AudioContext.currentTime` lookahead scheduling (25 ms scheduler tick, 100 ms lookahead). Per-scene **mood** picks a scale, BPM, and layer set:
- Menu: slow pad + sparse arp.
- Run: driving bass line + arp + synth-kick/hat drums; **intensity ramps** with run time and on boss spawn (adds a layer, raises BPM ~10%). Ducks under loud SFX bursts (sidechain via `musicBus.gain` automation).
- GameOver: descending minor pad.

All tempo/notes are data in `MusicGen` so it's tunable without new code.

## 9. Save / persistence

`SaveManager` writes a versioned `MetaSave` JSON via **@capacitor/preferences** (falls back to `localStorage` in browser). Saved on: meta change, app pause (`visibilitychange`), game-over. `SaveSchema` includes `version`; `migrate(old)` upgrades older saves. Contents: meta gold, gems, character unlocks, permanent upgrade levels, equipped gear/tech-parts, settings (audio volumes, haptics, quality override), and best-run stats. **In-run state is never persisted** (roguelite runs are ephemeral) — only the meta layer.
